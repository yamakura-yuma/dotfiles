設計・構成・調査結果を伝えるときは、**集めた情報をそのまま出さない**。相手が判断を
下すのに必要な最小限まで削ってから見せること。

- 全体像はまず図か表で見せる。対応関係（ファイルと配布先、イベントと所有者、層と責務）は
  散文よりも表のほうが速い。
- 調査の過程、検討して採らなかった選択肢は書かない。結論と、そこに至った理由を 1〜2 行
  足すだけにする。
- 計画ファイルも同じ方針で書く。「調査で判明したこと」を網羅する節を作らない。

長い散文の計画書は読まれない。数百行の Markdown を出して「読むのがあまりにきつい」と
差し戻された実績がある。

## 図を見せろと言われたら、実際にレンダリングする

Markdown の中に Mermaid を貼るだけでは足りないことがある。`show-me` スキルは単一の HTML
ファイルを生成してブラウザで開けるようにするもので、「図で見せて」と言われたときに
期待されているのは**その実物**である。構成や設計を見せるよう求められたら、Markdown 内の
図で済ませず、開ける成果物を生成して渡すこと。
