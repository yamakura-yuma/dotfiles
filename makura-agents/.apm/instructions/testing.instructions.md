## テストを書く

振る舞いを変えたら、その振る舞いを確かめるテストを一緒に書くこと。テストを後回しに
すると、動いていることを確かめる手段が「読み返して納得する」しか無くなる。

- 既存のテストの置き場所と書き方に合わせる。無いリポジトリなら、そのリポジトリで一番
  素直な方法（Go なら `_test.go`、シェルなら実行可能なスクリプト）で始める。
- 直したバグには、**直す前に失敗することを確認したテスト**を付ける。失敗を見ていない
  テストは、そのバグを捕まえられると分かっていない。
- 通る側だけでなく、通ってはいけない側も書く。ガードレールの類は特にそうで、「止めたい
  ものが止まる」より「止めたくないものが止まらない」ほうが壊れやすい。

## 検証コマンド

リポジトリに `.agent/verify.sh` があれば、それがそのリポジトリの検証手順。実行可能なら
実行し、出力を読むこと。無ければ、リポジトリの README や既存の設定から検証方法を探す。

この規約を共有しているのは呼び出し方だけで、中身は各リポジトリが決める。ビルドもテスト
も静的解析も言語ごとに違うので、共通化できるのは名前だけになる。

## 報告

**テストで確かめていないことを「動きます」と書かないこと。** これは書き方の問題ではなく、
事実の問題として守る。

- 検証を実行したなら、何を実行してどうなったかを書く。テストが落ちたなら、落ちたと
  出力付きで書く。飛ばした手順があるなら、飛ばしたと書く。
- 確認できていないものは「未確認」と書く。曖昧にぼかすより、そのほうが次の判断が速い。
- 自分の変更を自分で検証すると、通したい方向に評価が寄る。重要な検証は `verifier`
  サブエージェントに回すこと。あれは Edit も Write も持たないので、赤を緑にする手段が
  なく、赤をそのまま報告するしかない。
