## 設計の選び方

architect の手順で opus、sonnet、haiku の 3 モデルに設計案を並列で出させました。方針は 3 案とも同じでした。メールは必須、Slack は送れたら送る、メールの後に送る、の 3 点です。同じ Claude 系列だけでの一致なので、別系列のモデルの検証は入っていません。

| 案 | 形 | 判定 |
|---|---|---|
| c1 (opus) | 共通の `_post_json` と `notify_slack` | 土台に採用 |
| c2 (sonnet) | `(環境変数, 関数)` の登録リストを `ship_order` がループで回す | 見送り。項目が 1 つしかない登録リストで、有効かどうかの判定もリストと関数に分かれる |
| c3 (haiku) | HTTP の処理を複製し、`except Exception: pass` | 見送り。失敗の跡が何も残らない |

c1 から 1 点だけ変えました。c1 は Slack の本文に顧客のメールアドレスを入れていました。依頼にない個人情報なので外し、本文は注文 ID だけにしています。

案どうしの採点役は立てていません。3 案の方針がそろい、残った差は複雑さの判断だけで、それは ponytail-review の観点で決められたためです。

## 判断に効いた原則

- **Laziness Protocol。** SMS や LINE のための抽象（通知先の Protocol や登録リスト）は今は作りません。いまの `order` には電話番号がありません。LINE はトークン認証なので、Webhook URL と同じ形になる保証もありません。実物が 1 つもないまま形を決めると、推測で固めることになります。一方 `_post_json` は呼び出し元が 2 つあるので切り出しました。
- **Model the Domain。** 登録リストを持ち込むかどうかはこの原則で判断しました。いま消える分岐がないので「抽象を無理に入れない」側を取りました。3 つ目の通知先が来て、`ship_order` に同じ形の呼び出しが並び始めたら、構造に移す合図です。
- **Redesign from First Principles。** Slack を足すなら初めから 2 つのチャネルがあった形にしました。そのため `send_email` の中の HTTP の処理を共通化しています。
- **Test Behavior, Not Implementation。** テストは、実際に POST された URL の列と本文の JSON をリテラル値で比べます。実装をわざと壊して 3 通り試しました（実測）。
  - Slack を送らない実装にすると 2 件が失敗しました。
  - Slack の例外を上に投げる実装にすると 1 件がエラーになりました。
  - 未設定なのに送ろうとする実装は、最初は全件通りました。`Request(None)` の例外が握りつぶされ、URL の列が変わらないためです。未設定のテストに `assertNoLogs("shop")` を足し、この変異も落ちることを確かめました。
- **Prove It Works。** 実装担当のサブエージェントが、ローカルの `http.server` にモックなしの `urlopen` で送りました（実測）。Slack に届く場合は `/mail` と `/slack` の両方に想定どおりの本文が届きました。閉じたポートを指した場合は警告ログが出て、メールだけが届き、状態は `shipped` でした。

## 作業の割り振り

- **先に済ませるべき手順。** 設計の比較と統合を終えてから実装に入りました。
- **並列にできる作業。** 対象外です。変更は 2 ファイルで、互いに依存しています。
- **共有する書き込み先。** 対象外です。書き込んだのは実装担当 1 人だけです。
- **最小の分け方。** 実装担当 1 人にしました。コードが 20 行ほどなので、分けると調整の手間のほうが大きくなります。

レビュー時に、実装担当のテストと既存テストが重なっていたので 1 本にまとめました。また実装担当は「元の `shop.py` はスタブだった」と報告しましたが、事実と違います。`git diff` で元のコードとの差分を確かめ、変更は契約どおりでした。

## 未決の点

どれも私が既定の判断で進めたものです。
- **Slack が失敗しても出荷は成功扱い。** 出荷はもう起きているので、社内向けの通知の失敗で呼び出し元を止めない判断です。Slack の失敗も例外にしたい場合は「厳格」と言ってください。
- **メールが失敗したら Slack は送らない。** 顧客に届いていない出荷を社内に流さないためです。
- **メール失敗時に状態が `shipped` のまま残る問題。** 以前からあるもので、この変更では触っていません。
- **通知の待ち時間。** HTTP を直列に 2 回呼ぶので、最悪で約 20 秒待ちます（推測。タイムアウト 10 秒が 2 回と見た値です）。
