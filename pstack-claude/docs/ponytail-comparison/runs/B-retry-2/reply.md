## 変えたこと
- **リトライ条件。** `get_stock` は HTTP 5xx、`URLError`、`TimeoutError`、`ConnectionError` のとき最大 3 回まで試します。間は 1 秒待ちます。
- **リトライしないもの。** 4xx と、JSON 不正のようなそれ以外の例外は、初回でそのまま投げます。
- **3 回とも失敗したとき。** 最後の例外をそのまま投げます。最後の試行のあとは待ちません。
- **調整する場所。** 回数と待ち時間は `client.py` 冒頭の定数 `MAX_ATTEMPTS` と `RETRY_DELAY_SECONDS` です。運用してから変えるときは、ここだけ直せば済みます。
- **一時的な失敗の判定。** `_is_transient` の 1 か所にまとめました。`HTTPError` は `URLError` のサブクラスなので、`HTTPError` を先に判定します。コメントはこの理由の 1 行だけです。

## 判断に効いた原則
- **Laziness Protocol。** 環境変数での設定、`RetryPolicy` 型、デコレータ、指数バックオフを入れませんでした。「あとで調整したい」には、1 か所の定数 2 つで足ります。
- **Model the Domain。** 一時的かどうかの判定を `except` 節に散らさず、純関数 `_is_transient` の 1 か所に置きました。
- **Boundary Discipline。** 例外の分類は HTTP という境界の関数の中で閉じています。公開面は `get_stock(sku)` だけのままです。
- **Exhaust the Design Space。** 設計案を 1 本で済ませず 3 本並べました。その比較で待機の差し替え方の違いが見え、ラッパーと setter を落とせました。
- **Test Behavior, Not Implementation。** テストは `get_stock` だけを呼びます。戻り値、送出された例外そのもの（`assertIs`）、呼び出し回数、待ち秒数をリテラル値で確かめます。`_is_transient` を直接テストするケースは作りませんでした。
- **Prove It Works。** サブエージェントの報告を信じず、自分でテストとミューテーションを実行しました。
- **Never Block on the Human。** 途中で質問せず、最後まで進めました。
