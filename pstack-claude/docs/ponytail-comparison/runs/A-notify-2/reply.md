出荷時の Slack 通知を実装し、`feature` ブランチにコミットしました（`f0ff2cc`）。

**運用側から見た変化。** `SLACK_WEBHOOK_URL` を設定すると、出荷のたびにその Webhook へ `{"text": "Order 42 shipped."}` が POST されます。未設定か空文字なら、今までどおりメールだけです。Slack が落ちていても出荷は成功し、WARNING ログが 1 件出るだけです。メールが失敗したときは今までどおり例外になり、Slack は送りません。

**コードを引き継ぐ人から見た変化。** `shop.py` の構成は 4 つの関数になりました。
- `_post_json` は、JSON を POST する処理を 1 か所にまとめた関数です。
- `send_email` は外から見た挙動を変えていません。
- `send_slack` は、Slack を送るかどうかの判定と失敗時の扱いを自分の中で完結させています。
- `ship_order` はチャネルごとに 1 行ずつ呼ぶだけです。

SMS や LINE が来たときは、`send_*` 関数を 1 つ足し、`ship_order` に 1 行足せば済みます。

**検証。**
- `python3 -m unittest` は 5 件すべて通りました（実測）。
- モックを使わずローカルの HTTP サーバーに実際に送る確認もしました（実測）。メールだけの場合、メールと Slack の両方の場合、Slack に接続できない場合の 3 つとも期待どおりでした。
- テストでは、送信先 URL と送ったデータを具体的な値で確かめています。また `clear=True` を付けたので、開発者の手元に `SLACK_WEBHOOK_URL` が入っていてもテスト結果は変わりません。

**設計の経緯（architect）。** Opus・Sonnet・Haiku の 3 モデルに別々に設計させたところ、3 案とも同じ骨格にまとまりました。チャネル共通の抽象は作らない、Slack はベストエフォート、メールの挙動は変えない、の 3 点です。ただし 3 モデルとも Claude 系なので、この一致の重みは異なるベンダー間の一致より弱いと見ています。

| 案 | 形 | 扱い |
|---|---|---|
| Haiku | `send_slack` を `send_email` と並べ、`ship_order` から続けて呼ぶ | ベースに採用 |
| Opus | 何かを送る前に Slack の URL を検証する。Slack 本文に顧客のメールアドレスを入れる | テストで環境変数を消す工夫と、捕まえる例外を絞る方針を取り込んだ。事前検証は `ship_order` に処理順の決まりを増やすので不採用。メールアドレスは個人情報を Slack に流すので不採用 |
| Sonnet | `notify_shipped` を挟み、各 `send_*` が自分の失敗時の扱いを持つ | 「失敗時の扱いは各関数が持つ」を取り込んだ。呼び出し元が 1 か所しかない中継関数は不採用 |

**判断に効いた原則。**
- **Laziness Protocol。** 通知チャネルの登録表や Notifier プロトコルは作りませんでした。代わりに、重複していたリクエスト組み立てを `_post_json` にまとめただけです。
- **Model the Domain。** SMS や LINE はまだ確定していないので、今は構造を増やしませんでした。この原則は、分岐が減らない抽象を避けるよう求めています。
- **Exhaust the Design Space。** 1 案で決めず、3 案を出してから比べました。
- **Test Behavior, Not Implementation。** 「呼ばれたかどうか」ではなく、送信先 URL と送ったデータの具体的な値で確かめています。
- **Prove It Works。** モックの単体テストだけで終わらせず、実際の HTTP 送信でも確認しました。
