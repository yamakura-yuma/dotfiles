**挙動**
- HTTP 5xx、タイムアウト、接続エラーのときはリトライします。
- 4xx と、レスポンスに `quantity` がないような想定外の失敗は、1 回目でそのまま例外を投げます。
- 最大 3 回まで試し、間に 0.5 秒と 2.0 秒待ちます。3 回とも失敗したら、最後の例外を型もトレースバックも変えずに投げます。
- レスポンス本文の読み込み中に起きたタイムアウトもリトライします。

**運用しながら調整する方法**
- `client.py` の `RETRY_DELAYS = (0.5, 2.0)` の 1 行を書き換えるだけです。試行回数は「待ち時間の個数 + 1」で決まります。たとえば `(1, 2, 4)` にすれば 4 回試します。
- 回数と待ち時間を別々の定数にしなかったのは、二つが食い違う状態を作れないようにするためです。
- リトライのたびに warning ログを 1 行出します。調整の判断材料にするためです。

**設計の進め方と結果**
architect スキルで、Claude 系の 3 モデル (opus、sonnet、haiku) に設計案を別々に出させました。

| 案 | 形 | 判定 |

| 1 | 待ち時間のタプル 1 つに回数と間隔をまとめる。最終試行を try の外に出す | 採用 |

**考え方が効いた箇所**
- 最小の変更に絞るという考え方で、案 3 の汎用化と上の補助関数を捨てました。
- 問題の構造をデータで表すという考え方で、試行回数を待ち時間のタプルから導く形にしました。
- テストは振る舞いを確かめるという考え方で、テストは返り値、例外そのもの (`assertIs`)、呼び出し回数を具体的な値で確かめています。
- 本物で確かめるという考え方で、モックのテストとは別にローカルの HTTP サーバーでも確かめました。

**検証**

- 本物の `urlopen` をローカル HTTP サーバーに向けて、5 ケースすべて期待どおりでした。
