## 挙動

- HTTP 5xx、タイムアウト、接続エラーのときはリトライします。試行は最大 3 回です。
- 1 回目の失敗の後に 0.5 秒、2 回目の後に 1.0 秒待ちます。最後の試行の後は待ちません。
- 4xx と、応答の JSON が壊れているときは、1 回目でそのまま例外を投げます。
- 3 回とも失敗したら、3 回目の例外をそのまま投げます。バッチ側の既存の `except` 節はこれまでどおり効きます。
- 回数と待ち時間は `client.py` の `RETRY_DELAYS = (0.5, 1.0)` の 1 行で変えられます。試行回数は要素数に 1 を足した数です。
  - `(1.0, 2.0, 4.0)` にすると 4 回試行します。
  - `()` にするとリトライしません。

- **実サーバー。** 本物の `urlopen` をローカルの HTTP サーバーに向けて動かしました（スクリプトは `/tmp/arena-retry/verify_real.py`、コミットはしていません）。結果は次のとおりです。

| シナリオ | 結果 |
|---|---|

## 判断を左右した原則

- **Boundary Discipline。** 「一時的な失敗か」の判定を純粋関数 `_is_transient` の 1 か所に集めました。`HTTPError` は `URLError` のサブクラスです。`HTTPError` を先に判定しないと 404 までリトライしてしまうので、この順序の注意もその関数だけに書いてあります。
- **Model the Domain。** 回数と待ち時間を別々の定数にせず、待ち時間のタプル 1 つから回数を導く形にしました。2 つの値がずれる状態を作れなくなります。
- **Laziness Protocol。** 案 1 にあったタイムアウト値の定数化はやめました。今回の範囲外だからです。型注釈や docstring も、既存ファイルに合わせて付けていません。
- **Test Behavior, Not Implementation。** テストはすべて `get_stock` を通します。検証しているのは戻り値、投げられた例外が最後の例外そのものであること、リクエスト回数、待ち秒数です。`_is_transient` を直接たたく表形式のテストは入れていません。
- **Prove It Works。** 単体テストに加えて、上の実サーバーでの検証をしました。

## 残っている判断

- **PR は作っていません。** 依頼がコミットまでだったからです。
- **DNS 解決の失敗と TLS エラーもリトライします。** `HTTPError` 以外の `URLError` をすべて一時的な失敗として扱っているためです。設定ミスのような恒久的な失敗でも 3 回試すことになり、余計にかかるのは最大 1.5 秒です。
- **429 (Too Many Requests) はリトライしません。** 指示どおり、4xx として即座に投げます。API がレート制限をかけるなら、別途検討が必要です。
- **リトライの記録。** 捨てた 5xx 応答は明示的に閉じておらず、参照が消えた時点で CPython が閉じます（推測です。テストで GC 時に閉じられて警告が出たことからそう判断しています）。リトライが起きたことはログにも出ません。運用で回数を調整するときに頻度が知りたければ、ログを 1 行足すのが次の一手です。
