**設計（architect スキル）。** Opus、Sonnet、Haiku の 3 モデルに、同じ前提資料から別々に設計案を出させました。3 案とも同じ形になりました。行を作る非公開関数を 1 つ置き、形式ごとに公開関数を 1 つ持たせる形です。形式名で振り分ける仕組みと Exporter クラスの継承階層は、3 案とも独立に却下していました。ただし 3 モデルはすべて Claude なので、この一致は別系統のモデル間の一致より弱い根拠です。案が収束していたので、別モデルに採点させる工程は飛ばしました。Opus 案をベースにし、ponytail-review の観点で次の 2 点を削りました。
- `FIELDS` 定数。現時点で読むのは CSV のヘッダだけです。XML 側は `r.items()` で列順が取れるので、今は要りません。
- 説明用の docstring。周りのコードにはなく、読めばわかる内容でした。

**判断に効いた原則。**
- **Laziness Protocol。** 形式レジストリや `export(users, fmt)` のような振り分け関数は作りませんでした。3 形式なら関数を 1 つずつ置くほうが短く、呼び出し側に形式名の文字列という新しい概念も持ち込みません。
- **Model the Domain。** 共通部分を「整形済みで並べ替え済みの行のリスト」という 1 つの値として切り出しました。形式を足しても分岐は増えず、関数が 1 つ増えるだけです。
- **Minimize Reader Load。** 行を dict のまま `DictWriter` と `json.dumps` にそのまま渡しています。dataclass のような行型は作りませんでした。変換の層が増えるうえ、読む人が得るものが何もないからです。
- **Test Behavior, Not Implementation。** 既存の `test_json` は id の並びしか見ておらず、キーや整形が崩れても通ってしまう作りでした。そこで出力全体を文字列で比較する形に書き直しました。
- **Prove It Works。** テストが通るだけでなく、リファクタ前後の出力を突き合わせる比較スクリプトで等価性を確かめました。スクリプトが差分を拾えることも確認しています。
