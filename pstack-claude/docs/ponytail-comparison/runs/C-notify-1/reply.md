## 作ったもの

- `shop.py:10` の `_post_json` は、JSON を POST する処理です。URL、ヘッダ、timeout はここにまとめ、メールと Slack の両方がこれを使います。
- `shop.py:22` の `notify_slack(text)` は、Slack を使うかどうかと、失敗しても例外を出さない方針を、この関数の中で決めます。そのため `ship_order` には1行足すだけで済みました。
- 送る順番はメールが先で、Slack が後です。メールが失敗すると今までどおり例外になり、その場合 Slack には送りません。
- テストは4本です。未設定ならメールだけ、設定時は Slack に送る本文が期待どおり、Slack が失敗しても出荷は成功、メールが失敗したら Slack を試さない、の4つです。環境変数は `clear=True` で固定しているので、手元のシェルに `SLACK_WEBHOOK_URL` が残っていても結果は変わりません。

## 設計の選択と理由

architect スキルで設計案を3つ（opus、sonnet、haiku）並行に作らせ、比較しました。記録は `scratchpad/arena-notify/synthesis.md` にあります。

| 案 | Slack が失敗したとき | 失敗を握る場所 | 結論 |
|---|---|---|---|
| c1（opus） | ログだけ残し、例外は出さない | `notify_slack` の中 | 土台に採用 |
| c2（sonnet） | ログだけ残し、例外は出さない | `ship_order` の try/except | 不採用。通知先を増やすたびに `ship_order` の try/except も増える |
| c3（haiku） | 例外を外に出す | 外に出す | 不採用。再試行されると顧客にメールが二重に届く |

- **principle-exhaust-the-design-space** に従い、まったく同じ形の案だけで決めないよう、失敗時の扱いが異なる3案を並べてから選びました。c1 と c2 は別々に同じ振る舞いへ行き着いています。ただし3つとも Claude 系のモデルなので、この一致は他社のモデルを混ぜた場合より弱い根拠です。
- **principle-laziness-protocol** に従い、SMS や LINE のための通知レジストリや Notifier 抽象は作りませんでした。来期に実際に必要になったら、`notify_slack` と同じ形の関数を1つ書き、`ship_order` に1行足せば対応できます。共通化したのは、今すでに重複している JSON POST だけです。
- **principle-model-the-domain** は、使うかどうかの判断に使いました。通知先は2つだけで、この先増えるかもわからないため、通知先を管理する構造（テーブルなど）は作る価値がないと判断しました。このリポジトリは型のない辞書を使っていて、注文データの形は `order` の辞書のまま変えていません。
- **principle-test-behavior-not-implementation** に従い、テストは「呼ばれたかどうか」ではなく、送り先 URL の並びと、実際に送られた JSON の中身を具体的な値と比べます。
- **principle-prove-it-works** に従い、テスト以外にも実物で確かめました。
  - ローカルの HTTP サーバーを実際に立て、`ship_order` に本物の POST を送らせました。未設定ではメールだけが届きました。設定時は `/slack` に `{'text': 'Order 42 shipped'}` が届きました。Slack 側に接続できない場合も、戻り値は `shipped` でした。
  - わざとバグを入れて、テストが落ちることも確かめました。Slack の呼び出しを消すと2本が失敗しました。例外を握る処理を外すと1本がエラーになりました。

## 決めてほしいこと

- Slack の timeout はメールと同じ10秒にしています。Slack が遅いと、発送処理が最大10秒止まります。短く（たとえば3秒に）するかどうかを決めてほしいです。
- Slack に送る文面は `Order <id> shipped` だけにしています。顧客のメールアドレスなど個人情報は載せていません。
- メールの送信に失敗しても、`status` は `shipped` のまま例外が出ます。これは今回の変更の前からある挙動で、今回は手を入れていません。直す場合は別の作業として扱うのがよいと考えています。
